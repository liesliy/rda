RDA 开源/闭源模块拆分方案

路径 B：开源指标层 + 闭源推荐引擎 · 实施指南

推荐策略

将 RDA 拆分为开源核心（基础审计指标 + LeRobot 适配 + 报告模板）和商业版（模型感知推荐引擎 + 置信度规则 + 安全边界 + 批量处理/API）。开源部分进 LeRobot/HF 社区拿流量和信任，闭源部分作为付费产品的核心壁垒。

开源 — 公开源码，社区可用
闭源 — 仅商业版包含
条件性 — 视验证结果决定

架构分层总览

模块拆分明细

rda/metrics

开源

基础指标计算：idle_ratio、spike_count、effective_motion_ratio、duration、distribution、integrity 等。

base.py · distribution.py · integrity.py · motion.py · temporal.py

开源理由：这些是 Tier-1 universal metrics，定义已在技术文档中公开。开源后社区可验证和复现，建立信任。竞品（Calibra）已开源类似能力，不开源反而显得刻意隐藏。

rda/audit

开源

审计规则引擎：rules.py 定义 PASS/REVIEW/EXCLUDE 判定逻辑，episode_audit.py 和 dataset_audit.py 执行逐层审计。

rules.py · episode_audit.py · dataset_audit.py

开源理由：审计是 RDA 的基础能力，规则逻辑透明有助于社区信任。这部分壁垒不高，但开源后能成为 LeRobot 生态的"标准审计工具"。

rda/io

开源

数据加载与格式适配：LeRobot v2.1/v3.0 格式读写、自动格式检测、EpisodeData schema。

lerobot_loader.py · schema.py

开源理由：LeRobot 格式适配是社区贡献的基础设施。开源后可获得社区维护和扩展（如新格式支持），降低自身维护成本。

rda/report

开源

报告生成：聚合统计、JSON 报告、摘要、top issues 排序、audit history。

aggregation.py · json_report.py · summary.py · top_issues.py · audit_history.py

开源理由：报告模板是展示审计结果的工具，开源可让社区自定义报告格式，增加工具粘性。不包含推荐逻辑。

rda/cli

开源

命令行接口：提供 rda audit 命令的入口和参数解析。

main.py

开源理由：开源版只暴露 rda audit 命令，不含 rda recommend。CLI 是社区使用的入口，必须公开。

rda/recommend/engine.py

闭源

推荐规则引擎核心：模型类型感知分支（frame_wise vs temporal）、置信度等级（HIGH/EXPERIMENTAL/NOT_RECOMMENDED）、安全边界约束、Recommendation 数据结构。

RecommendationAction · ConfidenceLevel · TargetPolicy · _apply_rules()

闭源理由：这是 RDA 的核心差异化。模型类型感知 + 置信度规则 + 安全边界是竞品没有的能力。一旦公开，两周内可被复制。必须保留为商业版核心。

rda/recommend/temporal_metrics.py

闭源

Temporal sufficiency 完整计算：idle/active 分割、active_run 分布、valid_window_ratio、transition 密度、bimodal_gap 阈值检测。

TemporalSufficiency · DatasetTemporalSufficiency · _find_bimodal_threshold()

闭源理由：虽然指标本身是"观测性"的，但完整的 temporal sufficiency 框架是 recommend 引擎的数据基础。如果开源这部分，等于开源了 recommend 的输入管线，壁垒大幅降低。

rda/export

闭源

清洁数据集导出：基于审计结论自动裁剪 bad episodes，支持 conservative/aggressive 策略，自动重写 meta/info.json。

clean_export.py

闭源理由：export 是"审计→行动"闭环的关键一步。开源版只给诊断结果，商业版给出可执行的导出方案。这也是付费转化的关键功能点。

rda/calibration

条件性

Reference calibration + PCA behavioral scoring：参考数据集校准、MAD-based z-score、PCA composite deviation score。

reference.py · scorer.py · normalization.py · portable.py

条件性理由：calibration 有学术价值（可发论文），但如果企业客户愿意为"跨数据集比较"付费，则应保留为商业版功能。建议：先闭源验证付费意愿，若 3 个月内无企业客户关注此功能，可开源指标层（reference.py）保留 scorer.py。

rda/ui_app

条件性

Streamlit Web UI：上传数据集、查看审计结果、episode 浏览器、健康概览、导出操作。

app.py · pages/1_Upload.py · pages/2_Audit.py · ...

条件性理由：UI 可以是很好的获客工具（降低使用门槛），但也可能是商业版的卖点（"托管 Web 服务"）。建议：开源一个最简版（只展示 audit 结果），完整功能（含 recommend 展示）保留为商业版/托管版。

代码拆分实施步骤

  1. 创建双包结构

    将当前 robot-data-audit 仓库拆分为两个 Python 包：rda-core（开源，PyPI 发布）和 rda-pro（闭源，私有 PyPI 或直接分发）。rda-core 依赖 rda-pro 不存在的模块通过 try/except 降级处理。

  2. 拆分 rda/recommend/ 目录

    将 rda/recommend/ 整个目录从开源仓库移到闭源包。开源版 CLI 中 rda recommend 命令改为打印提示："推荐引擎为商业版功能，请安装 rda-pro"。保留 rda/recommend/__init__.py 的空壳以不破坏 import。

  3. 拆分 rda/export/ 目录

    同理将 rda/export/ 移入闭源包。开源版只输出审计报告（诊断），不提供自动裁剪导出（行动）。

  4. 处理 rda/calibration/ 依赖

    calibration 被 recommend 引擎依赖。方案：将 calibration 中的 normalization.py 和 portable.py 保留在开源版（基础指标标准化），reference.py 和 scorer.py（PCA scoring）移入闭源包。

  5. 调整 CI/CD 和 PyPI 发布

    开源版继续用 GitHub Actions 发布到公共 PyPI（包名 robot-data-audit）。闭源版使用私有 PyPI 或 GitHub Releases + 手动安装。考虑使用 license key 或激活码机制。

  6. 准备开源版 README 和文档

    开源版 README 突出：审计能力、LeRobot 兼容性、社区贡献指南。闭源版文档突出：recommend 引擎、模型感知推荐、企业级功能。

风险与应对

风险 1：开源后无人关注

开源版缺少 recommend 功能，可能被认为"只是个审计脚本"而无人问津。
应对：配合 HF blog / LeRobot 社区帖子做推广，强调"开源审计 + 商业推荐"的分工。提供 demo 数据集和可视化报告截图吸引关注。

风险 2：闭源版获客困难

没有开源社区的信任基础，直接卖闭源产品难。
应对：先用开源版积累 10-20 个真实用户，通过审计报告的价值建立信任后，再推荐升级到商业版获取 recommend 能力。

风险 3：拆分增加维护成本

两个包意味着两套版本、两套 CI、两套文档。
应对：初期可以用 monorepo 结构（同一仓库、两个 setup.py），后续用户量起来后再物理拆分。当前阶段优先逻辑分离，不急于物理拆分。

风险 4：竞品快速跟进

Calibra 等开源项目可能快速加入类似 recommend 功能。
应对：闭源版持续迭代实验数据和安全边界规则，建立"经过 N 个真实数据集验证"的信任壁垒。开源版保持指标层的社区领先地位。

建议时间线

Phase 1
WRC 前

逻辑拆分 + 开源准备

  • 在现有仓库中完成目录结构逻辑分离（不动 PyPI 发布）
  • 选定 License（推荐 Apache 2.0）
  • 补充 CONTRIBUTING.md + demo 数据集
  • 代码扫描：移除凭证、硬编码路径
Phase 2
WRC 期间

开源发布 + 社区推广

  • repo 从 private 改为 public
  • 发布 HF blog + LeRobot 社区帖子
  • 利用 WRC 热度做技术宣传
  • 收集早期用户反馈
Phase 3
1-3 个月

商业验证

  • 用免费额度拉 10-30 个真实用户试用 recommend
  • 验证：是否有人愿意付费？最卡的功能是什么？
  • 评估 calibration 是否开源
  • 根据反馈决定是否物理拆分双包
Phase 4
3 个月后

规模化或调整

  • 若企业客户为主 → 继续闭源 + 私有化部署
  • 若社区声量重要 → 开源 calibration 指标层
  • 若"没开源就没人信" → 开源一版可复现实验
  • 根据数据决定是否提高定价或增加功能
